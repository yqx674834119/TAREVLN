# 实机接入准备

当前没有机器人传输端；`ros_motion_gate.py` 只向 `/readiness/guarded_cmd_vel` 发布测试数据。训练得到的关节策略不会部署到实体机器狗。真实控制走厂商支持的高层运动接口。

硬件资料填入 `config/readiness/hardware-profile.json`：机器狗具体型号、计算平台、控制仓库及固定提交、SDK、相机/雷达、定位来源和标定包。只有这些资料明确后才能确定 CPU 架构、依赖版本、坐标变换和实际传输。

## 先完成无运动接入

1. 保存现有机器狗配置、软件版本及启动方式，建立独立部署目录，不覆盖已有导航或厂商控制服务。
2. 在只读模式核对相机内参、RGB/深度配准、雷达到机体外参、IMU 方向、时间戳及传感器频率。记录静止和人工搬运数据；不发送运动指令。
3. 用真实传感器和估计定位替换当前理想位姿与虚拟四方向图像。单前向相机需要实际转动获得新视角，不能把模拟四视图当作现成硬件能力。
4. 重放记录到 TARE/VLM，将速度仅接到门控测试出口，验证定位退化、时延、失联和数据异常时归零。此阶段仍无机器人传输。
5. 实现厂商 SDK 适配器，验证设备侧指令过期、连接丢失和物理急停行为。主机门控停止发布，不能替代设备端看门狗。任何现有避障或急停设置的关闭都不沿用。

## 首轮现场测试所需证据

版本固定的源码/依赖清单、标定与坐标链、完整回放报告、G1–G3 仿真报告、机器狗高层接口静态和无运动验证、设备侧看门狗记录、明确回退步骤，以及操作者确认可用的物理急停。确认本轮场地、速度、时间和运动授权后才启动实体运动。

当前缺少型号与传感器资料、实际 SDK 和设备侧验证；文档与仿真通过都不能替代这些证据。
