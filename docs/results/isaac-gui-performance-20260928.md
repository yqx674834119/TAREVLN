# Isaac GUI、观测可视化与性能实测

2026-09-28；部署目录：5090 的 `/home/yqx/VLN/cross-building-floor-nav`；分支：`codex/sysnav-system-parity`。

已实现 GUI 启动、性能采集、物体 ID/三维坐标图层、VLM 请求文字和图片，以及 `-1` 无限运行预算。当前仿真仍慢于实时：修改后两次短运行的实时因子为 0.152–0.159。本次验收针对启动、观测与停止链路，不构成目标导航成功或实机验收。

## 使用方式

1. 打开前端 `http://127.0.0.1:8878/`，选择 Isaac 任务，勾选 **Isaac Sim GUI**，开始仿真。GUI 在 **5090 已有的 xrdp 桌面 `:10`** 打开，需要从远程桌面查看；Mac 上的 Web 前端继续显示采样观测。
2. 运行预算选择 **-1 · 不限时**，可持续运行到任务停止、错误或手动停止。完整 SysNav 同时取消 VLM 调用次数上限。碰撞、失稳、定位失败等检查保持有效。Habitat 基准仍使用其固定动作预算。
3. 在 **TARE 规划与轨迹 → 物体 ID / 位置** 切换物体标记。标签显示原生 `/object_nodes_list` 的 ID、类别及 `(x, y, z)`，坐标单位为米，属于当前导航地图坐标系；不是场景真值。回放只取当前规划时间之前的对象快照。
4. 决策卡展示实际发送给 VLM 的消息文字及图片缩略图，保留角色和输出结构要求；移除“选择依据”。这里展示 API 请求和可观察输出，不展示隐藏推理。旧运行未保存请求时不会补造请求。
5. 前端服务重新启动可使用 `bash scripts/start_dashboard.sh`。脚本仅复用可访问的现有桌面，不启动新显示服务；任务运行期间不要重启前端。GUI 启动前检查桌面访问，VLM 启动前检查现有 API relay。

已验证 Isaac 创建窗口 `Isaac Sim Python 5.1.0`，使用场景中的 `/World/ReviewCamera`。关闭窗口或前端“停止本次”会停止所属运行。主循环保持 `world.step(render=False)`，显式调用 `world.render()`，避免控制周期之外意外增加物理步数。

## 性能证据与指标口径

实测文件位于 `data/sim/office/runs/<运行名>/report.json` 和 `runtime_metrics.jsonl`。RTF 定义为主循环中的仿真时间增量 / 墙钟时间增量，排除 Isaac 加载和初始化；表中仿真秒来自报告的仿真时钟读数。墙钟时间不代表从点击按钮到结束的总等待时间。

| 运行名 | 仿真秒 | 循环墙钟秒 | RTF | 渲染更新 FPS | GUI 新状态 FPS | 结束原因 |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| `gui-perf-baseline-20260928` | 19.915 | 175.765 | 0.1133 | 4.85 | 1.14 | 时间预算到达 |
| `ui-20260928-154654-f78bb` | 10.515 | 66.062 | 0.1592 | 6.94 | 1.61 | 手动停止 |
| `ui-20260928-155328-e1b9d` | 6.015 | 39.620 | 0.1516 | 7.19 | 1.54 | 手动停止 |

第二次运行由前端 API 以 `duration=-1, gui=true` 启动，取消 API 次数上限，并通过所属任务的停止接口结束。第三次从浏览器勾选 GUI、选择 30 秒预算后启动，提前手动结束；并未完成 30 秒。三次均通过接触检查。样本长度和热身状态不同，不据此声称统计显著加速，也不计作导航成功率。

- **渲染更新 FPS**：显式 Kit 渲染更新次数 / 墙钟秒，含传感器热身时对相同物理状态的重复渲染；不是独立机器人状态频率，也不是 RDP 客户端的显示帧率。
- **GUI 新状态 FPS**：物理推进之后的常规 GUI 刷新次数 / 墙钟秒。主循环每 20 个物理步刷新一次，物理步长 5 ms；当前约 1.5–1.6 FPS，与 RTF 一致。
- **VLM API 耗时**：网络调用往返时间，含服务端响应等待；不等于 DeepSeek 模型内部纯推理时间。统计包含已完成的失败调用，记录状态便于核对。
- **YOLO / SAM 耗时**：对应模型调用区段的测量，CUDA 同步后记录；不包括所有 ROS 排队、融合和界面绘制时间。

第二次运行的 VLM API 平均耗时为 **985 ms**，末次为 **1026 ms**；末次 YOLO 为 **32.36 ms**，SAM 为 **30.85 ms**。第三次 SAM 末次为 63.28 ms，可见单次值有波动。前端显示末次测量值，无测量时显示等待/空值，不填充虚假的 0 ms。

## 瓶颈与四 GPU 分配

| 组件 | 当前资源 | 说明 |
| --- | --- | --- |
| Isaac 渲染 | GPU 0 | GUI 与观测渲染 |
| YOLO | GPU 1 | 独立语义检测节点 |
| SAM | GPU 2 | 独立语义融合节点 |
| VLM 节点 | 进程可见 GPU 3 | DeepSeek 使用远端 API，当前没有本地 VLM 推理负载，GPU 3 可用于后续加速 |
| PhysX / LiDAR raycast / GICP | CPU | 当前经过验证的执行路径 |

设置 `CUDA_DEVICE_ORDER=PCI_BUS_ID` 和各节点 `CUDA_VISIBLE_DEVICES`；使用项目内 NVIDIA 580.173.02 动态库兼容包装器，未重启系统或替换全局驱动。

基线循环墙钟占比：传感器渲染与编码 **38.1%**，LiDAR raycast **24.0%**，物理与 GUI **15.2%**，ROS 桥接 **9.1%**，GICP **6.2%**。修改后的第二次运行对应占比为 29.1%、18.9%、23.2%、12.1%、8.0%。这些是对应代码区段的累计墙钟时间，不是 GPU profiler 的 kernel 利用率。

主要限制是同步采集链：全景相机轮换多个方向，每个方向至少渲染四次，第三视角再渲染八次；LiDAR 对每束射线逐个调用 CPU PhysX 查询。上述工作暂停主循环推进。DeepSeek 在 ROS 节点异步执行，不能把一次约 1 秒的网络等待当作每个物理步的阻塞时间。仅把检测模型放到更多 GPU 不能消除这个瓶颈。

本次已预计算 LiDAR 固定射线方向、批量执行姿态变换及命中坐标重建，并移除重复的压缩点云写入；保留射线模式、碰撞过滤和坐标契约。

直接切换 GPU 物理的探测运行 `gui-gpuphysics-probe-20260928` 在 `world.reset()` 初始化关节时失败：

```text
torch.arange(count, device=device)
RuntimeError: CUDA error: no kernel image is available for execution on the device
```

这表明现有 Isaac Python 环境的该 CUDA/PyTorch 路径与 RTX 5090 不兼容，不能把“有四张卡”视为 GPU 物理已经可用。交付代码保留 CPU 物理；探测报告留存，没有把失败配置设为默认。

后续优化顺序：

1. 使用持续存在的多相机 render products，同一物理状态采集各视角；在验证无旧帧、无黑帧和观测方向一致后，减少重复热身渲染。
2. 将逐束 Python raycast 迁移到批量 GPU 查询或 RTX LiDAR，验证量程、遮挡、自身碰撞排除、坐标系与时间戳；不能直接换传感器后沿用原有验收结论。
3. 在独立环境验证支持 RTX 5090 的 Isaac/CUDA/PyTorch 组合，再处理 Go2 控制器的 NumPy 与 GPU Tensor 接口。无需通过重启或全局覆盖依赖来试错。
4. 将可视化 JPEG 编码和日志压缩从控制关键路径移走，在同一场景、传感器配置和固定测试时长下重测 RTF 与导航行为。
